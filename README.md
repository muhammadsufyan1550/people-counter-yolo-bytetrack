# People Counter 🎯

Real-time people, bicycle, and car detection with line-crossing counting —  
built as a portfolio project for a **Computer Vision & AI Deployment Engineer** role.

---

## Pipeline Architecture

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         people-counter pipeline                         │
└─────────────────────────────────────────────────────────────────────────┘

  Video Source                Detection              Tracking
  ┌──────────┐    RTSP/file   ┌──────────────┐      ┌───────────────┐
  │ Webcam   │ ─────────────► │ YOLOv8n      │ ───► │ ByteTrack     │
  │ MP4 file │   OpenCV       │ (people,     │      │ (persistent   │
  │ IP cam   │   VideoCapture │  cars, bikes)│      │  track IDs)   │
  └──────────┘                └──────────────┘      └──────┬────────┘
                                                           │
                        Line-Crossing Logic                │
                        ┌─────────────────────────────────┘
                        │
                        ▼
               ┌─────────────────┐    IN / OUT     ┌─────────────┐
               │ Virtual Line    │ ───────────────► │  SQLite DB  │
               │ (Y = 67% frame) │  per-class event │  events.db  │
               └─────────────────┘                  └──────┬──────┘
                        │                                  │
                        ▼                                  ▼
               ┌─────────────────┐              ┌──────────────────┐

               └─────────────────┘              │  GET /stats      │
                                                └──────────────────┘
```

## Project Structure

```
people-counter/
├── config.py         # All tunable parameters (source, model, line, RTSP, frame-skip)
├── database.py       # Thread-safe SQLite wrapper with run_id session scoping
├── tracker_state.py  # Shared in-memory state (FPS, counts, reconnecting) between threads
├── video_loop.py     # YOLO + ByteTrack + line-crossing + OpenCV display + RTSP reconnect
├── api.py            # FastAPI endpoints (/counts, /events, /stats)
├── main.py           # Entry point — starts threads and Uvicorn
├── export_onnx.py    # Export YOLOv8n to ONNX format (run once)
├── benchmark.py      # Compare PyTorch vs ONNX Runtime FPS on 200 frames
├── requirements.txt  # Pinned dependencies
├── pedestrians.mp4   # Test video (not committed to git)

├── yolov8n.onnx      # Exported ONNX model (generated by export_onnx.py, not committed)

```

## Running

```bash
# Activate venv first (see above), then:
python main.py
```

- **OpenCV window** opens showing live detections, track IDs, line, counts, and FPS.  
- **API** is live at `http://localhost:8000` — open `/docs` for interactive Swagger UI.
- Press **Q** in the OpenCV window to stop.  
- With `LOOP_VIDEO = False` (default), the loop stops cleanly at EOF and prints a summary.

### Key config flags (`config.py`)

```python
VIDEO_SOURCE     = "pedestrians.mp4"   # 0=webcam, file path, or rtsp:// URL
LOOP_VIDEO       = False               # True → loop file endlessly; False → stop at EOF
FRAME_SKIP       = 1                   # 1=every frame, 2=every 2nd, 3=every 3rd
RTSP_MAX_RETRIES = 5                   # reconnect attempts on stream drop
RTSP_RETRY_DELAY_S = 2.0              # seconds between reconnect attempts
CLEAR_DB_ON_STARTUP = False            # True → wipe old events on each run
```

### ONNX export & benchmark

```bash
# Export PyTorch model to ONNX (run once; produces yolov8n.onnx)
python export_onnx.py

# Compare PyTorch vs ONNX Runtime FPS on 200 frames
python benchmark.py
```

## Results

All measurements on **Intel Core i3-2130 @ 3.40 GHz, CPU only, Windows 11, 1920×1080 input**.

### Baseline FPS (full pipeline: decode + track + draw + display)

| Mode | FPS |
|------|-----|
| `FRAME_SKIP=1` (every frame) | **2.2** |
| `FRAME_SKIP=2` (every 2nd frame) | **4.4** |
| `FRAME_SKIP=3` (every 3rd frame) | **5.2** |

*Frame-skip FPS is measured over 200 frames including video decode and display.*

**Accuracy note:** At `FRAME_SKIP=2` or `3`, a fast-moving person can cross the entire counting line between two inferred frames and be missed entirely. On this CPU (2.2 FPS baseline) the temporal gap between inferences is ~450 ms at skip=2 — large enough to miss some crossings in a busy scene. On a GPU at 30+ FPS baseline, skip=2 is nearly lossless.

### ONNX vs PyTorch (pure inference, 200 frames pre-loaded into RAM, no display)

| Backend | FPS | Speedup |
|---------|-----|---------|
| PyTorch CPU | **3.3** | 1.00× |
| ONNX Runtime (CPUExecutionProvider) | **4.6** | **1.41×** |

**Why ONNX Runtime is faster here (3 lines):**  
PyTorch carries the full autograd and training graph at runtime even during inference. ONNX Runtime strips all of that, applies graph-level optimisations (operator fusion, constant folding) and dispatches through MLAS (Microsoft's optimised CPU linear algebra library). The 1.41× gain is typical for CPU-only YOLOv8n. The real gain comes on GPU: with the CUDA Execution Provider or a TensorRT EP, the same model achieves 3–6× over PyTorch CPU.

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| ByteTrack via `model.track(persist=True)` | Zero extra install; Ultralytics bundles it |
| Line-crossing via prev/current Y comparison | Simple, no duplicate counts, no extra state |
| `run_id` column in DB | ByteTrack resets IDs to 1 each run; `run_id` scopes all queries to current session |
| SQLite over PostgreSQL | Zero-config for a single-node prototype |
| Background thread for video loop | Keeps Uvicorn's async event loop free; clean shutdown via `stop_event` |
| `tracker_state.py` shared module | Decouples video loop from API without a message queue |
| `YOLO_AUTOINSTALL=0` env var | Prevents Ultralytics from installing packages into system Python during export |

## Limitations & Future Work

> **Honest statement:** This project ran entirely on CPU on a Windows PC. None of the following are implemented in the code — they are described as future steps only.

| Feature | Status | Future step |
|---------|--------|------------|
| **GPU / CUDA / TensorRT** | ❌ Not implemented | Install CUDA toolkit + `torch+cu12x`, replace `CPUExecutionProvider` with `CUDAExecutionProvider`; use `trtexec` to convert ONNX → TRT engine for 3–6× further speedup |
| **Face recognition** | ❌ Not implemented | After person detection, crop the face ROI and run InsightFace or DeepFace to identify individuals; store `person_id` in events table |
| **License plate recognition (LPR)** | ❌ Not implemented | After car detection, crop the plate ROI and run EasyOCR or PaddleOCR; store plate text in events table |
| **Multi-camera support** | ❌ Not implemented | Spawn one `video_loop` thread per RTSP URL, prefix every event row with a `camera_id` column, and fan out to separate API routes or a shared DB |
| **Docker deployment** | ❌ Not implemented | Write a `Dockerfile` (python:3.11-slim base), `docker-compose.yml`, and `--gpus all` flag for NVIDIA runtime; mount the model and config as volumes |
| **Ubuntu / Linux deployment** | ❌ Not implemented | Same code runs on Linux; replace `venv\Scripts\activate` with `source venv/bin/activate`, add `systemd` service file for auto-restart |
| **RTSP reconnect (exponential backoff)** | ⚠️ Basic only | Current code uses fixed `RTSP_RETRY_DELAY_S`; production should use exponential backoff with jitter to avoid thundering herd on camera restart |
| **PostgreSQL** | ❌ Not implemented | Replace `sqlite3` with `asyncpg` + SQLAlchemy; handles concurrent writers across cameras and network clients |

## Top 5 Interview Questions — Tier 3 Features

**Q1: "What is ONNX and why would you use it instead of keeping the PyTorch model?"**  
> ONNX is a vendor-neutral graph format. You export once from PyTorch, then run the same file on ONNX Runtime (CPU/GPU), TensorRT, OpenVINO, or CoreML — without PyTorch installed. This matters for deployment: a lean Docker image for inference doesn't need the full PyTorch training stack (~1 GB+). In this project we saw 1.41× speedup on CPU just from the runtime switch.

**Q2: "How does your RTSP reconnect work, and what would you improve in production?"**  
> On `cap.read()` failure, we release the handle, set `reconnecting=True` in shared state (visible via `/stats`), then call `cv2.VideoCapture()` again up to `RTSP_MAX_RETRIES` times with a fixed `RTSP_RETRY_DELAY_S` sleep. In production I'd replace the fixed delay with exponential backoff (2s, 4s, 8s…) plus jitter to prevent all cameras reconnecting simultaneously after a network event. I'd also add a `camera_id` to every log line and event row.

**Q3: "Your benchmark shows 3.3 FPS PyTorch vs 4.6 FPS ONNX Runtime. What would you expect on an NVIDIA GPU with TensorRT?"**  
> On a mid-range GPU (e.g. RTX 3060), PyTorch with CUDA typically hits 60–100 FPS for YOLOv8n at 640px. TensorRT with FP16 can push that to 150–200+ FPS via kernel fusion and reduced precision. The path is: `export_onnx.py` → `trtexec --onnx=yolov8n.onnx --saveEngine=yolov8n.trt --fp16` → load the engine with `tensorrt` Python bindings or ONNX Runtime's TensorRT EP.

**Q4: "What happens to track IDs and counts when the video file loops or when an RTSP stream reconnects?"**  
> On file loop (`LOOP_VIDEO=True`) or RTSP reconnect, we call `prev_cy.clear()` and `counted_ids.clear()` to discard stale Y-positions and prevent double-counting. The in-memory counters (`in_counts`, `out_counts`) are **not** reset — they keep accumulating, which is correct for a live camera but over-counts for a looping test file. ByteTrack's internal ID counter is not reset either, so IDs keep incrementing across reconnects. We handle cross-run DB contamination with the `run_id` column that scopes all queries to the current process.

**Q5: "How would you scale this to 8 cameras simultaneously?"**  
> Each camera gets its own `video_loop` thread (or process for true CPU isolation), its own `cap` object, and logs events with a `camera_id` column in the DB. The FastAPI layer gets `/counts?camera=cam1` query filters. For production I'd move to multiprocessing (one process per camera) or containerise each camera's loop in its own Docker container, with all containers writing to a shared PostgreSQL database over the network. A message queue (Redis Streams or Kafka) between the detection processes and the API decouples throughput spikes from the REST layer.
