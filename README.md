# People Counter

A learning project exploring a real-time video analytics pipeline in the style of CCTV analytics: detect people, bicycles and cars in a video, track them, count line crossings, store events, and expose live results through an API.

## Pipeline

```
Video source ──► Detection ──► Tracking ──► Line-crossing logic ──► SQLite ──► FastAPI
(file/webcam/    YOLOv8n       ByteTrack    (virtual line at        events.db   /counts
 RTSP URL)       (person,      (persistent   67% of frame height)               /events
 via OpenCV      bicycle,      track IDs)          │                          /stats
                 car)                              ▼
                                           OpenCV window
                                           (boxes, IDs, counts, FPS)
```

## Project Structure

```
people-counter/
├── config.py         # All tunable parameters (source, model, line, RTSP, frame skip)
├── database.py       # Thread-safe SQLite wrapper with run_id session scoping
├── tracker_state.py  # Shared in-memory state (FPS, counts, status) between threads
├── video_loop.py     # YOLO + ByteTrack + line crossing + OpenCV display + RTSP reconnect
├── api.py            # FastAPI endpoints (/counts, /events, /stats)
├── main.py           # Entry point: starts the video thread and Uvicorn
├── export_onnx.py    # Export YOLOv8n to ONNX format
├── benchmark.py      # Compare PyTorch vs ONNX Runtime FPS on 200 frames
├── requirements.txt  # Dependencies
```

Not committed to git (create or download locally):
- `pedestrians.mp4`: your own test video, placed in the project folder
- `yolov8n.pt`: downloaded automatically by Ultralytics on first run
- `yolov8n.onnx`: generated by `export_onnx.py`
- `events.db`: created automatically on first run

## Setup

```bash
# 1. Enter the project folder
cd people-counter

# 2. Create a virtual environment
python -m venv venv

# Windows
venv\Scripts\activate
# macOS / Linux
source venv/bin/activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Put a test video named pedestrians.mp4 in the project folder
#    (or change VIDEO_SOURCE in config.py)
```

YOLOv8n weights (~6 MB) download automatically on the first run.

## Running

```bash
python main.py
```

- An OpenCV window opens with detections, track IDs, the counting line, per-class counts and FPS.
- The API runs at `http://localhost:8000`. Open `/docs` for the interactive Swagger UI.
- Press `Q` in the OpenCV window to stop.
- With `LOOP_VIDEO = False` (default), the app stops at the end of the file and prints a summary.

## Key Config Flags (`config.py`)

```python
VIDEO_SOURCE        = "pedestrians.mp4"  # 0 = webcam, file path, or rtsp:// URL
LOOP_VIDEO          = False              # True = loop the file; False = stop at end of file
FRAME_SKIP          = 1                  # 1 = every frame, 2 = every 2nd, 3 = every 3rd
RTSP_MAX_RETRIES    = 5                  # reconnect attempts if the stream drops
RTSP_RETRY_DELAY_S  = 2.0                # seconds between reconnect attempts
CLEAR_DB_ON_STARTUP = False              # True = wipe old events on each run
```

## Results

All measurements were taken on an Intel Core i3-2130 @ 3.40 GHz, CPU only, Windows, 1920×1080 input video. This is old hardware, and numbers varied between runs (for example, the live `/stats` endpoint showed about 3.2 FPS at `FRAME_SKIP=1`, while the benchmark run below measured 2.2), so treat them as rough figures and the relative gains as the main finding.

### Frame skipping (200 frames of the test video)

| Mode | FPS |
|---|---|
| `FRAME_SKIP=1` (every frame) | 2.2 |
| `FRAME_SKIP=2` (every 2nd frame) | 4.4 |
| `FRAME_SKIP=3` (every 3rd frame) | 5.2 |

Skipping frames raises FPS but does not scale linearly, because every frame is still decoded and displayed; only inference is skipped.

**Accuracy trade-off:** skipping frames lowers temporal resolution. On a live stream, a fast-moving person could cross the counting line between two inferred frames and be missed. I did not measure the accuracy loss quantitatively.

### ONNX Runtime vs PyTorch (pure inference, 200 frames pre-loaded, CPU)

| Backend | FPS | Speedup |
|---|---|---|
| PyTorch CPU | 3.3 | 1.00× |
| ONNX Runtime (CPUExecutionProvider) | 4.6 | 1.41× |

ONNX Runtime applies graph-level optimizations (such as operator fusion and constant folding) and uses optimized CPU kernels, which gave about a 1.4× speedup here. I have not measured GPU or TensorRT performance; that is the next step.

## Key Design Decisions

| Decision | Rationale |
|---|---|
| ByteTrack via `model.track(persist=True)` | Built into Ultralytics (needs the `lap` package); no separate tracker to integrate |
| Line crossing by comparing previous and current Y position | Simple; a `counted_ids` set prevents counting the same track ID twice |
| `run_id` column in the database | Track IDs restart from 1 on every run; `run_id` scopes queries to the current run |
| SQLite instead of PostgreSQL | Zero configuration for a single-node prototype |
| Video loop in a background thread | Keeps the API responsive while the video loop runs |
| `tracker_state.py` shared module | Decouples the video loop from the API without a message queue |
| `YOLO_AUTOINSTALL=0` during export | Stops Ultralytics from trying to install packages into the system Python |

## Known Limitations

- Detection misses some small, distant or partly hidden people in crowded scenes (YOLOv8n at default settings).
- Track IDs can switch after occlusion (for example, behind a pole), so a person may be counted twice. `counted_ids` only prevents double counting of the same ID.
- A person who crosses the line, turns around and crosses again is not counted a second time.
- With `LOOP_VIDEO = True`, the in-memory counters keep accumulating across loops. This only affects the looping test file, not a live camera.
- Counts are approximate and were not validated against a manual ground-truth count.

## Limitations & Future Work

This project ran entirely on CPU on a Windows PC. The items below are **not implemented** unless stated otherwise; they are described as possible next steps only.

| Feature | Status | Possible next step |
|---|---|---|
| GPU / CUDA / TensorRT | Not implemented | Run on an NVIDIA GPU with CUDA, then convert the ONNX model to a TensorRT engine and measure the speedup |
| RTSP reconnect | Implemented, not tested against a live stream | Test with a local RTSP server (for example MediaMTX plus ffmpeg); add exponential backoff |
| Face recognition | Not implemented | Detect and align faces, compute embeddings (for example InsightFace) and match by similarity |
| License plate recognition | Not implemented | Detect plates on cars, then run OCR (for example PaddleOCR) |
| Multi-camera support | Not implemented | One processing loop per stream, with a `camera_id` column in the events table |
| Docker deployment | Not implemented | Write a Dockerfile and compose file; use the NVIDIA runtime for GPU |
| Ubuntu / Linux deployment | Not implemented | Run on Ubuntu as a systemd service |
| PostgreSQL | Not implemented | Replace SQLite to support concurrent writers across cameras |
